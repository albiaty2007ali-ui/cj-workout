# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

CJ WORKOUT is a Flask server-rendered web app (Arabic/Iraqi-dialect UI) combining subscription/payment management with a **local-first nutrition chat assistant**. "Local-first" is a hard architectural constraint here, not an implementation detail: there is no external LLM/nutrition API call at runtime. All food matching, quantity resolution, and calorie math run against a local SQLite database and hand-written Arabic NLP rules in this repo.

> **Note — parallel Netlify/TypeScript engine also exists in this repo.** Everything below in this
> file documents the *original* Flask/Python app (`nutrition_ai/`, `templates/`, etc.), which is
> still present and functional. A second, actively-deployed implementation of the same nutrition
> engine — TypeScript, ported layer-for-layer from `nutrition_ai/` — lives in
> `shared/nutrition-engine/` + `netlify/functions/` + `frontend/` (React), deployed to Netlify/
> Firebase. It is "local-first" in the same sense (calories/portions/business rules never come
> from an LLM), but it *does* optionally call Gemini as a bounded NLU layer — see
> **[AI_ARCHITECTURE.md](AI_ARCHITECTURE.md)** for that design and its safety guarantees. This
> CLAUDE.md was never updated when that migration happened; treat the Flask docs below as accurate
> for `app.py`/`nutrition_ai/` only, not for the Netlify/TS engine.

## Commands

```bash
# setup
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env              # then set a real SECRET_KEY:
python3 -c "import secrets; print(secrets.token_hex(32))"

# run (dev)
python3 app.py                    # http://127.0.0.1:5000

# run (prod)
gunicorn -w 4 -b 0.0.0.0:8000 "app:create_app()"

# rebuild the food DB from scratch (Iraqi/Arabic seed data only)
python3 scripts/import_foods.py --reset --seed

# add USDA Foundation Foods data (requires raw CSVs already downloaded)
python3 scripts/import_foods.py --usda data/raw/usda

# promote an existing registered user to admin
python3 make_admin.py user@example.com

# generate a real VAPID key pair for Web Push (run once per environment, copy output into .env)
python3 scripts/generate_vapid_keys.py

# run the automated test suite (conversation state machine + regressions)
python3 -m pytest tests/ -v
```

There is no linter or type-checker configured in this repo — don't invent commands for them. There **is** a `pytest` suite under `tests/` (added alongside the DIRECT_LOG feature) — run it after any change to `nutrition_ai/`. It uses an in-memory SQLite DB (`tests/conftest.py`), completely isolated from `instance/cjworkout.db`.

**Schema changes and the dev DB**: there is no migration tool (no Alembic). `db.create_all()` at startup only creates *missing tables*, it does not add columns to existing ones — so a new `User`/`MealLog`/etc. column (like `last_direct_log_json`) needs a manual `ALTER TABLE` against any existing `instance/cjworkout.db` you want to keep using, or just delete that file to let it rebuild fresh (fine in dev, never do this against real user data).

## Deployment

This is a stateful Python/Flask process — it does **not** run on static-site/serverless-JS hosts like Netlify or Vercel's default preset. `render.yaml` (Blueprint) is set up for [Render](https://render.com)'s free tier: `gunicorn -w 2 -b 0.0.0.0:$PORT "app:create_app()"`, `SECRET_KEY` auto-generated, `SESSION_COOKIE_SECURE=True`. `app.py` wraps `app.wsgi_app` in Werkzeug's `ProxyFix` so `url_for(_external=True)` (password-reset/welcome email links) and rate-limiting see the real client IP/scheme behind the platform's reverse proxy — keep that wrapper if you switch hosts, any PaaS behind a proxy needs it.

**Free-tier caveat, deliberate for now**: free Render web services have no persistent disk, so `instance/cjworkout.db` (users, meals, payments, XP...) and `static/uploads/*` (payment proofs, profile photos) are wiped on every redeploy/restart. `data/database/foods.sqlite` (the food knowledge base) is committed to git, so nutrition matching always works regardless. This is fine for trying the app out; before real users rely on it, either add Render's paid persistent disk or migrate `DATABASE_URL` to a managed Postgres instance (the app already reads `DATABASE_URL` from the environment — no code change needed for that swap, SQLAlchemy handles both) and move uploads to object storage.

## Architecture

### App wiring
`app.py:create_app()` is the Flask app factory: loads `.env`, configures SQLAlchemy/session/security headers, and registers nine blueprints — `main` (main.py), `auth` (auth.py), `payments` (payments.py), `chat` (chat.py), `admin` (admin.py), `profile` (profile_bp.py), `settings` (settings_bp.py — also hosts the Web Push subscribe/unsubscribe/preferences endpoints, no separate blueprint for those), `recipes` (recipes_bp.py), `progress` (progress_bp.py — `/daily` and `/progress/weight`, see "Daily meals + weight tracking" below). `db.create_all()` runs at startup against the SQLAlchemy models in `models.py`, followed by seed functions (`nutrition_ai.tips_engine.seed_default_tips`, `nutrition_ai.levels.seed_default_levels`, `nutrition_ai.streaks.seed_default_milestones`, `nutrition_ai.recipe_search.seed_default_recipes`, `nutrition_ai.notifications.engine.seed_default_notification_templates`) and `nutrition_ai.notifications.scheduler.start_scheduler(app)` — this is a **separate database** from the food knowledge base below. Note the module names `profile_bp.py`/`settings_bp.py` (not `profile.py`/`settings.py`) — deliberately avoids shadowing Python's stdlib `profile` module.

### Two separate databases — don't confuse them
- **App DB** (`instance/cjworkout.db`, configurable via `DATABASE_URL`): SQLAlchemy ORM models in `models.py` — `User`, `Plan`, `Subscription`, `Payment`, `NutritionProfile`, `MealLog`, `MealStatus`, `ChatMessage`, `ShownTip`, `WaterLog`, `NutritionTip`, `XPTransaction`, `ActiveDay`, `Level`, `StreakMilestone`, `Recipe`+family, `NotificationTemplate`, `PushSubscription`, `UserNotification`, `NotificationSettings`, etc.
- **Food knowledge base** (`data/database/foods.sqlite`): raw `sqlite3` (no ORM), schema owned by `food_db.py`, built/rebuilt only via `scripts/import_foods.py` from `foods_seed.py` (hand-curated Iraqi/Arabic foods) and optionally USDA CSVs. Uses FTS5 for alias search. Never write to this DB from request-handling code except through `food_search.py`.

### Nutrition chat pipeline — layered architecture in `nutrition_ai/`
`nutrition_engine.py` is now a **thin facade**: `handle_message(user, text, db, models, debug=False)` just re-exports `nutrition_ai.orchestrator.handle_message`, kept for backward compatibility with `chat.py`'s `/api/chat` endpoint. All real logic lives in `nutrition_ai/`, one file per layer:
- `intents.py` — keyword-based Intent Detector (`LOG_MEAL`, `ADD_FOOD`, `REMOVE_FOOD`, `CHANGE_QUANTITY`, `SWAP_FOOD`, `CORRECTION`, `WATER_LOG`, `WEIGHT_UPDATE`, `END_DAY`, `ASK_TIP`, `CONFIRM`, `CANCEL`, `OFFTOPIC`, `MEDICAL`, etc.) — `detect_intent(text, ctx)` where `ctx` carries `has_pending`/`has_recipe`/`has_undoable_log`/`has_pending_recipe`/`has_pending_food_topic`. Three intents distinguish "not yet eaten" mentions of a *specific* food from `EXPRESS_DESIRE`'s generic "أريد"/"يمكن": `EXPRESS_CRAVING` (`CRAVING_MARKERS`: "مشتهي"/"نفسي بـ"/"خاطري بـ" — deliberately **not** in `RECIPE_TRIGGERS`, since it previously was and caused whole-message free-text recipe search to false-positive-match unrelated recipes via fuzzy matching, e.g. "مشتهي" ~ "مشوي"), `PLAN_TO_EAT` (`PLAN_TO_EAT_MARKERS`: "راح آكل"/"ناوي آكل" — future tense, was previously unmatched anywhere and fell through to the `LOG_MEAL` default, wrongly starting a real meal-builder `pending` for a statement that isn't consumption), and `ASK_PORTION_FOR_FOOD` (`PORTION_QUESTION_MARKERS`: "شكد آكل"/"شكد لازم آكل" — checked with the highest priority of the three so a combined message like "مشتهي دولمة شكد لازم آكل؟" routes straight to a portion answer instead of a plain craving acknowledgement). None of the three ever log a meal.
- `entities.py` + `fuzzy.py` — Food Entity Extractor. Exact alias matching stays in `food_search.py` (`match_message_with_meta` also returns consumed spans); `fuzzy.py` runs `difflib` typo-tolerance on the *leftover* text only, with confidence tiers (`>=0.90` auto, `0.70–0.89` ask "تقصد X؟", ambiguous pairs ask "X لو Y؟"). Never invents a food that isn't in `foods.sqlite`.
- `quantity.py` — Arabic number words + water-volume units (`كوب`, `استكان`, `نص لتر`...), independent of any specific food.
- `meal_state.py` — explicit `DRAFT/CONFIRMING/CONFIRMED/CANCELLED` labels over the same `User.pending_meal_json` storage (`load_pending`/`save_pending`, replacing the old `_load_pending`/`_save_pending`).
- `corrections.py` — "لا خليها 3" (`change_last_quantity`), "شيل الجبن" (`remove_food`), "بدل X بـ Y" (`swap_food`, shows before/after kcal diff and requires a fresh confirm) — all operate on the in-flight `pending` dict only.
- `calculator.py` — the only place that calls `food_search.compute_nutrition`/totals; `macros.py` derives protein/carb/fat targets from the calorie target; `safety.py` is the single source of truth for the safe-calorie floor and max deficit/surplus (`calorie_calc.py` delegates to it).
- `tips_engine.py` + `tips_seed.py` — tips now live in the `NutritionTip` DB table (seeded once from `tips_seed.py`), not a hardcoded list; `choose_category_for_context()` picks a category from a small context object (see `context.py`).
- `recommendations.py`, `responses.py`, `provider.py` — recommendation search over `foods.sqlite`, varied response templates, and an `AIProvider` interface (`NullAIProvider` is the only implementation — no local LLM is wired up yet; it exists so one can be plugged in later purely for phrasing, never for calorie math).
- `orchestrator.py` — composes all of the above into one `handle_message()`; this is where the precedence order lives (off-topic/medical → cancel/confirm → corrections/swap/remove/change-qty → water/weight/tip → day-summary/remaining/suggestion intents → cooking assistant (`recipes_data.py`) → new-meal parse).

Meal logging is a state machine (labels in `nutrition_ai/meal_state.py`: `DRAFT`, `AWAITING_CLARIFICATION`, `AWAITING_CONFIRMATION`, `CONFIRMED`, `DIRECT_LOGGED`, `UNDO_WINDOW`, `UNDONE`, `COMPLETED`, `CANCELLED`), not a single-shot parse:
1. `entities.extract_food_entities()` tries to resolve each mentioned food to a gram quantity (exact match, then fuzzy).
2. **DIRECT_LOG (exception, not the default)**: if this is a brand-new message (no `pending` in flight) and *every* mentioned food resolved with zero clarifications needed, the meal is logged immediately — no "type yes to confirm" round-trip — via `orchestrator._try_direct_log()` → `_finalize_meal(..., source="direct")`. This only fires on a single fully-unambiguous message; it does **not** weaken the "no confirmation, no log" rule, it just recognizes that an unambiguous single message already *is* the confirmation. A short **undo window** (`nutrition_ai/direct_log.py`, `UNDO_WINDOW_SECONDS`, default 5 min) follows: a full snapshot (MealLog id, XP awarded, streak/free-meal state before, items) is stored on `User.last_direct_log_json`, so "لا"/"شيلها"/etc. can fully reverse it (`direct_log.undo()`), and a correction ("لا مو بيضتين، 3") transparently reopens it for editing (`direct_log.reopen_meal_for_edit()` — deletes the old `MealLog`, rebuilds a `pending` draft from the snapshot, requires a fresh explicit confirmation before it's logged again).
3. Anything not resolvable — ambiguous plural, "bulk" food like rice needing a portion, or a fuzzy guess needing confirmation — becomes a clarification question; the partial result is serialized to `User.pending_meal_json` so it survives across chat turns/requests.
4. Once a `pending` exists (the meal is being built across multiple messages), it **always** requires an explicit confirmation to log, even if a later message makes it fully unambiguous — DIRECT_LOG only ever applies to the very first message of a meal, never to a continuation. Follow-up messages resolve remaining clarifications, add newly-mentioned foods to the same pending meal, or apply a correction/swap/removal — multi-message meals accumulate into one `MealLog`, not several.
5. A `MealLog` row is only created via `orchestrator._finalize_meal()` — either an explicit confirmation phrase (`source="confirmed"`) or the DIRECT_LOG path above (`source="direct"`). This is a deliberate rule: **never guess a quantity or calorie count, never log without either an explicit confirmation or an unambiguous single-message statement of what was eaten.** Preserve this invariant in any change to the engine.
6. `nutrition_ai/intents.py`'s `EXPRESS_DESIRE` intent (triggered by markers like "أريد"/"يمكن"/"أفكر") guards against messages like "أريد بيض" being mistaken for consumption — this must stay checked before the default `LOG_MEAL` fallback, since several food aliases (e.g. "بيض") resolve with full confidence and would otherwise DIRECT_LOG on a mere expression of desire. `EXPRESS_CRAVING`/`PLAN_TO_EAT` (see above) guard the same invariant for "مشتهي"/"راح آكل"-style messages specifically.
7. `GENERAL_NUTRITION` — was a defined-but-dead intent constant (no trigger phrase and no handler existed) until a real trigger and handler were added: `GENERAL_NUTRITION_MARKERS` (question markers like "فايدة"/"مضر"/"اضرار") must co-occur with a `GENERAL_NUTRITION_TOPICS` word (protein/carb/fat/fiber/sugary drinks/fast food/desserts/pre-post-workout/meal timing) to fire — this compound condition is what keeps it from hijacking real food logging (e.g. "اكلت بروتين بار" stays `LOG_MEAL`). `orchestrator._general_nutrition_topic()` picks the specific topic (checked in priority order so "بروتين قبل التمرين" resolves to the more specific `pre_workout` topic, not the generic `protein` one) and answers via `responses.general_nutrition_answer()` — general education only, never a per-user number. `ASK_REMAINING` similarly gained macro-awareness: `orchestrator._asked_macro()` detects an explicit "بروتين"/"كارب"/"دهون" mention and answers with the real remaining grams for that macro (from `context.build()`'s `macro_targets`/`consumed_*` fields) via `responses.remaining_macro()`, instead of always defaulting to calories.
7. **Short-term food-topic memory** (`User.pending_food_topic_json`, same JSON-on-row pattern as `pending_meal_json`/`pending_recipe_confirmation_id`): when `EXPRESS_CRAVING`/`PLAN_TO_EAT` resolves a food entity, `orchestrator._handle_food_topic()` stores `{food_id, food_name, kind}` so a later bare follow-up like "شكد آكل؟" (no food named again) resolves via `orchestrator._handle_portion_for_food()`'s fallback to this stored topic rather than asking the user to repeat themselves. `intents.detect_intent()` gates `CONFIRM`/`CANCEL` on `has_pending_food_topic` the same way it already does for `has_pending_recipe`, so a bare "اي"/"ماريد" reply is interpreted relative to the pending food topic (never a global synonym). `nutrition_ai/recommendations.py:suggest_portion_for_food()` computes the actual suggested quantity from `food_search.get_portions_for()`/`calculator.compute_food()` — real portions and real per-portion calories only, never an invented gram conversion.

Non-negotiable rules baked into this engine (stated in `nutrition_engine.py`'s docstring — keep them true when editing):
- Calories/macros always come from `food_nutrients` in `foods.sqlite` via `nutrition_ai/calculator.py`, never estimated in code (and never by an LLM, if one is ever wired into `provider.py`).
- Quantities are resolved from explicit text (grams, named portions, Arabic number words) — never assumed.
- The bot never tells the user to stop eating; going over target triggers a non-judgmental "balance next meal" message (`orchestrator.compensation_message`), not restriction advice.
- **"Today" is always Baghdad's calendar day**, computed via `nutrition_ai/calculator.today_utc_range()` (converts Baghdad midnight-to-midnight into the equivalent naive-UTC range for comparison against `created_at` columns, which are stored via `datetime.utcnow()`). Never compare `date.today()` (server/local date) directly against a `created_at` column — they disagree for part of the day whenever the server's local date isn't UTC, which silently drops "today's" meals from totals.

### Debug Mode and the admin panel
`/api/chat` accepts `{"debug": true}` in the JSON body; the response only includes a `debug` key (intent, food candidates/confidence, meal state, tip selected, context used) when `current_user.role == "admin"` — silently ignored otherwise, even if a non-admin sends the flag. `admin.py` covers three admin-editable tables, all following the same pattern (list/add/toggle-or-update/delete, `auth.admin_required`, every action logged to `AdminLog`): `/admin/tips` (`NutritionTip`), `/admin/levels` (`Level`), `/admin/streak-milestones` (`StreakMilestone`). Full food/alias/portion administration is still exclusively through `scripts/import_foods.py` + `foods_seed.py`, not a web UI.

### XP, Streaks, and Levels
- **XP is a ledger, not just a counter**: `nutrition_ai/xp_engine.py:award_xp(user, amount, reason, source=None)` is the *only* place `user.xp` should change — it writes an `XPTransaction` row first. Passing `source` (e.g. a `MealLog` id, or `f"streak_milestone_{days}"`) makes the grant idempotent (calling it again with the same `source` for the same user is a no-op) — this is what stops a streak milestone from being paid out twice, and there is no reason to ever do `user.xp += n` directly anywhere else. `xp_engine.reverse_xp(...)` undoes a grant by writing a *negative* transaction with a `_undo`-suffixed source (never delete the original row — the ledger is an audit trail).
- **Streaks are derived from a real day-log, not a fragile counter**: `nutrition_ai/streaks.py:record_active_day(user)` inserts an `ActiveDay(user_id, date)` row for Baghdad's current date (the `UniqueConstraint` makes a second call same-day a no-op — multiple activities in one day never double-count), then updates `User.streak_days`/`longest_streak`/`streak_started_at` by checking whether yesterday's `ActiveDay` exists. It returns a snapshot dict (previous streak state + any newly-crossed `StreakMilestone`s, each already paid via `xp_engine.award_xp`) that `nutrition_ai/direct_log.py` stores verbatim (JSON-serialized) so a DIRECT_LOG undo/reopen can call `streaks.undo_active_day()` and reverse the milestone XP precisely. `streaks.days_absent(user)` and `streaks.recent_active_dates(user, days=30)` (profile calendar) are read-only derived views over the same table — don't add a second source of truth for "was the user active on day X."
- **Levels** (`nutrition_ai/levels.py:xp_progress(xp)`) read the `Level` table (seeded 1–30 by `seed_default_levels`, admin-editable) — never hardcode level thresholds/titles in a template or response string.
- These systems are deliberately minimal versions of what a full gamification layer could be — no notification delivery, no anti-abuse rate-limiting beyond the idempotent `source` key, no "friends" concept. Don't build UI for capabilities that don't exist yet (see Settings below).

### Profile, Settings, and what's intentionally not built
`profile_bp.py` (`/profile` own view, `/u/<username>` public view gated by `User.profile_visibility`, `/profile/edit` and `/profile/photo*` as JSON/AJAX endpoints so the page never full-reloads) and `settings_bp.py` (`/settings`, one section per concern) exist alongside the chat, not instead of it. Profile photos reuse the upload pattern from `payments.py:subscribe` (`secure_filename`, extension allowlist, size cap) plus real `Pillow` processing (center-crop to square, resize to 512px, re-encode as JPEG) — there is no client-side interactive cropper. "Delete account" (`settings_bp.py:delete_account`) never hard-deletes a `User` row — it sets `disabled=True` and scrubs name/username/bio/photo/email, preserving `Payment`/`Subscription` history for financial audit. Dark mode (`static/js/settings.js` + the `--bg`/`--surface`/`--text`/`--border` custom properties in `style.css`) is real and scoped to the new pages plus `body`'s base colors — it does **not** retheme the marketing hero, sidebar, or admin pages, which keep their explicit `--forest`/`--cream` colors. Deliberately absent, to avoid building UI against data that doesn't exist: meal/food preferences, notification toggles (no delivery mechanism exists), "friends"-tier privacy, and "log out of all devices" (would need a session-versioning mechanism that isn't there).

### Iraq-specific time and greeting logic
`iraq_time.py` computes the current period (morning/noon/evening/late_night) from `Asia/Baghdad` wall-clock time (not server time) and maps it to the relevant meal. `chat.py:build_greeting()` + `MealStatus` (per user/day/meal-type: `not_started → asked → logged`) ensure the same meal is never asked about twice in one day.

### Daily meals + weight tracking (`progress_bp.py`)
`/daily` ("يومي الغذائي") and `/progress/weight` ("متابعة الوزن") are read-first dashboards over data that already existed but was never aggregated or displayed: `MealLog` (has `meal_type`/`created_at` all along) and `WeightHistory` (was written on every weight update but only ever read once, for the `/settings/export` JSON dump — never rendered anywhere). Both pages pull from the same sources of truth used everywhere else, never recompute independently:
- `nutrition_ai/calculator.py:meals_by_type_for_day(user, MealLog, target_date)` groups today's (or any past day's) `MealLog` rows by `meal_type` — `breakfast`/`lunch`/`dinner` are single dicts (`{"status": "NOT_STARTED"}` or `{"status": "LOGGED", calories/protein/carbs/fat/foods/logged_at}`), `snack` is a list (supports more than one snack per day). **`matched_foods_json` is a JSON array of plain food-name strings** (`["بيض بالطماطة"]`), not objects — don't `map(attribute=...)` on it in a template, and never name a dict key `items`/`keys`/`values` if a Jinja template will dot-access it (`dict.items` silently resolves to the built-in method, not the key, and fails with a non-obvious `TypeError` at render time — this bit the first draft of `daily.html`, hence the `foods` key name here instead of `items`).
- `nutrition_ai/meal_budget.py:distribute_remaining_budget(remaining_calories, unlogged_meal_types, current_period)` — an intentionally modest budget split across *only the not-yet-logged* meals of the current day (already-logged meals are never touched/re-budgeted), weighted by `iraq_time.get_current_period()` so whichever meal matches the current time of day gets the larger share. It does not factor in activity level, training schedule, or hunger/preference — those aren't real data anywhere in this app, so they're deliberately not faked into the weighting. This is informational display only on `/daily`; it does not feed into or replace `nutrition_ai/recommendations.py`'s `ASK_RECOMMENDATION` logic in the chat.
- `nutrition_ai/weight_stats.py:compute_weight_stats()` computes `current/starting/average/lowest/highest_weight`, `total_change`, `trend` (`DECREASING/INCREASING/STABLE/INSUFFICIENT_DATA`, needs ≥3 points and a >0.3kg first-half-vs-second-half difference to call a direction — otherwise honest `STABLE`/`INSUFFICIENT_DATA`), `weekly_change` (only computed if a real entry exists 5–9 days back; otherwise `None` + a `weekly_change_note` string explaining why, never a guessed number), and `distance_to_goal`/`goal_direction` from `NutritionProfile.goal_weight` (new nullable field — no UI sets it except the weight-tracking page's own inline form) cross-referenced against the real `goal` field (`lose|maintain|gain`) so the direction language is never assumed to be "losing weight" by default.
- `nutrition_ai/weight_ops.py:apply_weight_update()` is the one place that recomputes BMR/TDEE/calorie target and appends a `WeightHistory` row (never overwrites a previous entry) — both `nutrition_ai/orchestrator.py`'s chat `WEIGHT_UPDATE` handler and `progress_bp.py`'s `/progress/weight/log` endpoint call this same function, so logging a weight from the chat or from the dashboard produces identical results.
- The weight chart is Chart.js (CDN, `templates/weight_progress.html`) reading only real `WeightHistory` points via `/progress/weight/chart-data` — no gap-filling, a 30-day view with one real entry draws one point. It reads `--moss` (not `--forest`) for the line color specifically because `--forest` is a near-black brand green that has almost no contrast against the dark-theme background — worth remembering before reusing `--forest` for any other data-visualization accent.
- There is no realtime/push sync between chat-side meal logging and an already-open `/daily` tab (no websocket/Firebase infrastructure exists in this project) — both pages simply reflect the database fresh on every load/refresh, identically to every other page here.

### Free tier / paywall
`User.free_meals_used` (capped at 6, see `User.free_meals_remaining`) is enforced **server-side only**, checked inside `nutrition_ai/orchestrator.py:_finalize_meal()` (the single place a `MealLog` gets created, for both the confirmed and DIRECT_LOG paths) — not at parse time. A user can go through the full clarification flow, or trigger DIRECT_LOG, but the meal isn't logged and `premium_required` is returned once free meals are exhausted. `chat.py` translates that into `PREMIUM_LOCK_MESSAGE` for the frontend.

### Payments
Subscriptions are activated manually, not via a payment gateway: users upload a bank-transfer proof image (`payments.py:subscribe`), which creates a `Payment` row (`pending_manual_review`). An admin (`admin_required` decorator — role check against the DB, never trust the frontend) approves/rejects it in `/admin/payments`, which is the only place a `Subscription` row gets created. All admin actions are written to `AdminLog`.

### Email
`email_service.py` sends transactional email (welcome, password reset, payment confirmed/rejected) via the Resend API. Email failures are always caught and logged, never allowed to block the underlying user action (registration, password reset request, payment review).

### Frontend
Server-rendered Jinja templates (`templates/`) with vanilla JS (`static/js/chat.js`, `onboarding.js`, `toast.js`, `profile.js`, `settings.js`) — no JS framework/build step. AJAX endpoints (`chat.py:api_chat`, `profile_bp.py`, `settings_bp.py`) validate CSRF manually via `validate_csrf(request.headers.get("X-CSRFToken"))` since they're JSON endpoints rather than WTForms POSTs; the token is embedded per-page as `window.CJ_CSRF_TOKEN`. `toast.js` exposes a global `showToast(message, category)` for any page to surface a non-blocking confirmation after an AJAX action — use it instead of a new toast mechanism. `static/css/style.css` has a global `[hidden] { display: none !important; }` reset — any class that sets its own `display` (`.modal-overlay`, `.tutorial-nav`, etc.) would otherwise win the cascade over the `[hidden]` attribute and stay visible; don't remove this rule.

### Recipe system
Real recipe data lives in the App DB, not `foods.sqlite` — `RecipeCategory`, `Recipe`, `RecipeIngredient`, `RecipeStep`, `RecipeSubstitution` in `models.py`. `nutrition_ai/recipes_seed.py` holds the only hand-curated seed data (the categories + the handful of recipes migrated from the old `recipes_data.py`); `nutrition_ai/recipe_search.seed_default_recipes()` (called once at startup from `app.py`, same pattern as `seed_default_tips`) migrates it idempotently — never invent additional recipes here, add them through `/admin/recipes` instead. Categories with no real recipes yet (e.g. حلويات, مشروبات حارة) are expected to render an honest empty state, not placeholder content.

`nutrition_ai/recipe_search.py:search_recipes(query, category_id)` is the single source of truth for recipe lookup — substring match (bidirectional, so a full chat sentence containing the recipe name matches, and so does a short partial query) plus word-level `difflib` typo tolerance restricted to `name`/`match_keywords` only (min word length 4, threshold 0.55) — deliberately **not** applied to `description`, because fuzzy-matching short/common words in prose descriptions produced false positives. `recipes_bp.py` exposes `/recipes` (browse+search UI), `/recipes/api/search` (JSON, called by `static/js/recipes.js` on a 300ms debounce), and `/recipes/<slug>` (detail + an in-page Tutorial mode driven by client-side JS/`sessionStorage` for step navigation, with two server round-trips at the boundaries only — see below).

The chat integration reuses `User.current_recipe_id`/`current_recipe_step` (now holding a real `Recipe.id`) exactly as before — `nutrition_ai/orchestrator.py`'s `ASK_RECIPE`/`COOKING_STEP` branches just read from `Recipe`/`RecipeStep`/`RecipeSubstitution` instead of the old dict. `intents.RECIPE_CATEGORY_PHRASES` deliberately uses multi-word phrases ("أريد حلو", "مشروب بارد", ...) rather than bare category words ("حلو", "شاي", "قهوة") — several of those words are real logged foods in `foods.sqlite` (e.g. "شاي"), so a bare-keyword trigger would hijack `اكلت شاي` into a recipe search instead of logging the meal. Never loosen this back to single-word category triggers without checking `foods_seed.py` for collisions first.

Admin CRUD lives in `admin.py` (`/admin/recipes` + nested ingredient/step/substitution/category routes, same list+add+toggle+delete+`AdminLog` pattern as `/admin/tips`) and reuses the `profile_bp.py` Pillow image pipeline (crop-to-square, resize, JPEG re-encode) for `static/uploads/recipe_images/`. A newly-added recipe starts `active=False` and the toggle route refuses to activate one with no ingredients or steps yet — this is what keeps an incomplete admin draft from ever being shown to users as a real recipe.

### Recipe → meal confirmation, and calorie-budget gating
**Finishing a recipe never logs calories by itself** — opening a recipe, starting the tutorial, and reaching the last step are all distinct from actually eating it. Reaching the last step (chat's `COOKING_STEP` branch, or the web tutorial via `recipes_bp.py:/recipes/<slug>/complete`) calls `orchestrator.mark_recipe_awaiting_confirmation(user, db, recipe)`, which clears `current_recipe_id`/`current_recipe_step` and sets `User.pending_recipe_confirmation_id` — a separate piece of state from the meal-builder `pending_meal_json`, checked via a new `has_pending_recipe` flag in `intents.detect_intent`'s `ctx`. Only an explicit "أكلتها" (or "اي"/"تمام"/etc., matched via `intents.RECIPE_EATEN_PHRASES` — deliberately gated behind `has_pending_recipe` so it's never a global CONFIRM synonym) routes to `orchestrator._finalize_recipe_meal()`, which builds a synthetic single-item `pending` from the recipe's real `calories`/`protein`/`carbs`/`fat` and calls the same `_finalize_meal(..., source="recipe")` used by every other meal path — same XP award, same streak update, and (since `"recipe"` is treated like `"direct"` for the undo-snapshot branch) the same 5-minute undo window as DIRECT_LOG, with zero duplicated logic. "بعدني" leaves `pending_recipe_confirmation_id` set (so a much-later "أكلتها" still logs correctly); "لا" clears it without logging. Priority order when a message could mean multiple things: an in-flight meal-builder `pending` always wins over a recipe confirmation, which always wins over a stale DIRECT_LOG undo window.

The `/recipes/<slug>/start` endpoint is the **only** place calorie budget blocks anything — reusing `nutrition_ai/context.build()`'s `over_target` (never recomputed by hand), it refuses to enter the tutorial for a *new* recipe once the user is already over their daily target, with a real backend check (not just a disabled button — `recipes.js` shows the blocked screen only after this endpoint says so). This must never be confused with logging: `_finalize_meal`/`_finalize_recipe_meal` never check the target and always log an explicit "أكلتها" truthfully, even over budget — the gate is about starting something new, not about refusing to record something that already happened. `_recipe_card()`'s `fits_remaining` field (and the non-blocking "⚠️ أعلى من سعراتك المتبقية" badge / "🎯 مناسب لسعراتي المتبقية" filter on the browse page) is informational only when not over target.

### Notification system — real Web Push, layered under `nutrition_ai/notifications/`
Real OS-level Web Push (Service Worker + Push API + VAPID), not an in-app-only UI — `static/sw.js` (served at the site root via `main.py:/sw.js`, required for its scope to cover the whole origin, not `/static/sw.js`) handles `push`/`notificationclick`; `static/js/push.js` registers it and calls `Notification.requestPermission()` **only** when the user explicitly flips "🔔 تشغيل الإشعارات" in Settings — never on page load. Four new tables: `NotificationTemplate` (admin-editable via `/admin/notifications`, same list+add+toggle+delete+`AdminLog` pattern as `/admin/tips`), `PushSubscription` (one row per browser endpoint), `UserNotification` (the sent-log — `dedup_key` + a `UniqueConstraint` on `(user_id, category, dedup_key)` is what makes double-sends impossible even across `gunicorn -w 2` workers: both workers may attempt a send, but only one's `INSERT` succeeds, the other's `IntegrityError` is caught in `engine.record_sent()` and treated as "already sent, skip" — no distributed lock needed), and `NotificationSettings` (one row per user, everything defaulted honestly — `enabled=False` until the user opts in).

- **`nutrition_ai/notifications/templates_seed.py`** — the only hand-written copy (seeded once via `engine.seed_default_notification_templates()`, same pattern as `tips_seed.py`); ~90 genuinely distinct templates across the 15 requested categories (BREAKFAST/LUNCH/DINNER/SNACK/WATER/HYDRATION/STREAK/XP/MOTIVATION/RECIPE/PROGRESS/RETURN/MEAL_REMINDER/DAILY_SUMMARY/CONSISTENCY) — a deliberate, documented choice over a literal "500+" ask: real variety beats padded near-duplicates. Add more only through `/admin/notifications`, never by inflating this file with palette-swapped copies.
- **`nutrition_ai/notifications/engine.py`** — all the decision logic in one place: `can_send_now(user, settings, category)` checks master/category toggles → `is_quiet_hours()` (handles the midnight-wraparound case, e.g. default 22:00→08:00) → daily limit (`UserNotification` rows sent today, Baghdad-day-aware via `calculator.today_utc_range()`) → cooldown (default 90 min, **tripled** once `NotificationSettings.consecutive_ignored >= 3` — the "خفف الإشعارات تلقائيًا لو تجاهلها" auto-decay). `pick_template(category, exclude_template_id=...)` is a priority-weighted random pick that excludes the user's last-sent template in that category, so the same exact message never fires twice in a row. **`send_notification(user, category, dedup_key, url)` is the single entry point actually used by both the scheduler and event-driven callers** — it never raises (wraps everything in `try/except`, mirroring `email_service.py`'s "a notification failure must never block the real action" rule).
- **`nutrition_ai/notifications/scheduler.py`** — `start_scheduler(app)` (called once from `app.py`) starts an in-process APScheduler `BackgroundScheduler` ticking every 5 minutes — deliberately not Celery/Redis, to match the single-Flask-process `render.yaml` deployment. Guarded against the Werkzeug dev-reloader's parent/child double-process split via `WERKZEUG_RUN_MAIN`/`FLASK_ENV` (only starts in the real child process during `FLASK_ENV=development`; starts unconditionally in production since gunicorn has no such split — the per-worker duplicate-send risk there is what the `UserNotification` unique constraint solves). `run_meal_reminder_tick()` compares Baghdad "now" against each user's configurable `breakfast_time`/`lunch_time`/`dinner_time` (±15 min tolerance window, deduped to once/day via `dedup_key=f"{category}_{today}"`), skips a meal already logged that day (reuses `MealStatus`, no new tracking), and substitutes a single gentle `RETURN` message instead of a normal reminder — once, not once-per-meal-window — when `streaks.days_absent(user) >= 3`. Set `NOTIFICATION_SCHEDULER_ENABLED=False` (already default in `tests/conftest.py`) to disable the background thread entirely, e.g. in tests, which call `run_meal_reminder_tick(app)`/etc. directly instead.
- **Streak-milestone pushes are event-driven, not polled**: `orchestrator._notify_streak_milestones()` is called right after `streaks.record_active_day()` produces `new_milestones` (in both `_finalize_meal` and `_handle_water_log`) — it reuses that already-computed real data (never re-derives "did they hit a milestone" separately) and calls `engine.send_notification(user, "STREAK", f"streak_{days}", "/profile")`, best-effort.
- **`nutrition_ai/notifications/push.py`** — thin `pywebpush` wrapper; `VAPID_PRIVATE_KEY_PEM_BASE64`/`VAPID_PUBLIC_KEY`/`VAPID_CLAIMS_EMAIL` come from `.env` (generate with `scripts/generate_vapid_keys.py`, run once per environment — rotating them invalidates every existing `PushSubscription`). Without real keys configured, `push.is_configured()` is `False` and sends no-op safely (confirmed by `tests/test_notifications.py::TestPushConfiguration`) — the rest of the system (settings, scheduler ticks, dedup) still works and is fully testable without ever needing real VAPID keys.
- Settings persistence (`settings_bp.py:/settings/notifications`, `/settings/push-subscribe`, `/settings/push-unsubscribe`, `/settings/vapid-public-key`) follows the exact same `postJSON`/manual-`validate_csrf` AJAX pattern as `ai-style`/`privacy`. `/settings/push-opened` (hit by `static/sw.js`'s `notificationclick` handler, which has no page-embedded CSRF token available) is intentionally the one unauthenticated-by-CSRF endpoint — it only sets an `opened_at` timestamp and resets `consecutive_ignored`, judged low-enough-risk to justify skipping the manual check there.

## Working in this codebase

- All chat-bot copy is Iraqi-dialect Arabic; match existing tone/phrasing (informal, "كابتن" as the user address) when adding bot replies.
- When adding new food-matching behavior, prefer extending `food_search.py`/`foods_seed.py` (or `nutrition_ai/fuzzy.py` for typo-tolerance) over adding special-casing in `nutrition_ai/orchestrator.py`. When adding a new chat capability, add an intent in `nutrition_ai/intents.py` and a handler branch in `orchestrator.py` rather than growing one existing branch with unrelated logic.
- `.env` holds real secrets (Resend API key, etc.) and must never be committed; `.env.example` is the template.
